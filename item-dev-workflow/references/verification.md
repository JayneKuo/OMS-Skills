# 测试与验证约定

## 开发前

- 先与用户确认本次改动的验证方式
- 明确最小验证单元
- 测试先行：先编写或补充对应测试用例，再进入功能实现

最小验证单元优先选择：

1. 单个方法或单个 service 用例
2. 单个 controller 接口
3. 单个模块内最小可闭环流程

## 测试目录

新增测试用例默认放在项目根目录下的 `tests/`。

- 单元测试优先放在 `tests/unit/`
- 集成测试优先放在 `tests/integration/`
- 端到端测试优先放在 `tests/e2e/`
- 除非用户明确要求，否则不要把新增测试散落到业务源码目录旁边

## 开发后验证

完成一轮开发后，必须根据当前项目的技术栈和启动方式实际拉起服务。

选择启动命令时优先看：

1. 项目现有的启动脚本或 README
2. 构建工具中的标准运行命令
3. 具体模块的可执行入口

如果项目存在多个模块或多个启动入口，优先选择与本次改动直接相关的那个服务进行验证。

## 验证失败后的处理

如果验证不通过，不要只停留在报错结果；应继续排查、修改并重新验证，直到问题收敛或可以明确说明阻塞原因。

## 收尾

当开发结束且所有测试用例通过后，整理本轮开发过程中出现的错误、误判、返工点或可复用经验，并主动询问用户是否需要将这些内容更新到文档、流程或 skill 中。

## 提交与合并流程

开发自测通过后，按以下步骤提交并合并到测试分支：

1. 暂存业务代码变更（只 add 业务文件，不提交 `.claude/`、`CLAUDE.md` 等工具文件）：

```bash
git add <业务文件路径>
```

2. 提交到当前开发分支：

```bash
git commit -m "feat/fix: 简要描述

- 变更点1
- 变更点2

Co-Authored-By: Claude Sonnet 4 <noreply@anthropic.com>"
```

3. 推送开发分支到远端：

```bash
git push origin <开发分支名>
```

4. 切换到 staging 分支，拉取最新，合并开发分支：

```bash
git checkout staging
git pull origin staging
git merge <开发分支名> --no-edit
```

5. 如有冲突，解决后重新 `git add` 冲突文件，再 `git commit`。

6. 推送 staging 到远端，切回开发分支：

```bash
git push origin staging
git checkout <开发分支名>
```
